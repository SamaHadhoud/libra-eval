# K2-V3 Chat Red-Teaming - Phase 1 Look-back and Phase 2 Plan

Answers two questions: **(1)** what we did for K2-V3 and how to reproduce its scores given an
endpoint; **(2)** resources and time to get the same score set for the 4–5 K2-V3 family
models (different sizes), and whether we can run them all in parallel.
All figures are measured from the completed V3/V2 runs, not projected.
*(Command-level detail and pitfalls: `K2V3_FAMILY_RED_TEAM_PLAYBOOK.md`.)*

## At a glance — 5 models

| | |
|---|---|
| **Judge-API cost (full score set)** | **$800–1,000** total (≈$160–200 per model; main scores only: $200–250 total) |
| **Compute wall-clock, all 5 in parallel** | **~1 day** (serial: 3–4 days) |
| **Manual work** | 5–7 person-days incl. the family report (report numbers/tables/charts auto-generate) |
| **Calendar end-to-end** | **~2 work weeks** — scores final in week 1, report + contingency in week 2 |

## Phase 1 look-back: what produced the V3 scores

**Suite:** 95 tasks × n=200 = **17,825 prompts** (88 main-English → headline + 10 domain
tables; 3 multilingual; 4 UAE). **Judge:** the V3 anchor was scored by GPT-4o; new family
runs use **GPT-5.6-terra** (0.93 correlation / 95% agreement with 4o, stricter, ~35% cheaper
— see the judge study). 80 tasks LLM-judged,
15 programmatic (free). **Harness:** one workstation, I/O-bound; ~250 MB disk per model.

| Stage | What happens | Per-model cost |
|---|---|---|
| **A. Main suite** *(automated, ~12 h)* | 17,825 generations (reasoning traces stored) + 14,859 judge calls on final answers → all headline/domain scores | ~$40–50 |
| **B. Thinking divergence** *(automated, 2–4 h)* | Judge-only pass over Stage A's stored traces: 12,232 calls, **zero new generations** — traces in, structured verdicts out, hence pricier than A | ~$100–130 |
| **C. UAE comparison** *(cached)* | New models answer the 4 UAE tasks inside Stage A; GPT-4o-mini and V3 baseline results are frozen and reused | $0 |
| **D. Reports & deltas** *(automated — built)* | **One family report covering all sizes** (no per-model reports). Results layer is generated by `family_report/`: every number as a `\famnum` LaTeX lookup, 16 table fragments, 5 cross-size charts (scaling curves, domain bars, trade-off, heatmap) — add a model to `models.json`, rerun 2 scripts; verified identical to the published V3 report data | — |

**Parallelism model:** tasks run **serially** within a run; the 200 items of each task are
sent **concurrently** — ~100 in flight against V3's local vLLM server, and 40 against V2's
hosted API (`api.k2think.ai`), the client-side cap we set after higher concurrency
triggered 429 storms on that key (tunable per endpoint via `K2_CONCURRENCY`; each new
endpoint gets its own safe value from the Step-1 rate probe). Models parallelize as
separate processes. Task-sharding across processes is possible (per-task files, no
collisions) but only cuts wall-clock if the endpoint has serving capacity beyond ~100
concurrent — the ~12 h is endpoint-bound, not harness-bound.

**Measured per-task wall-clock** (from run logs; judging interleaves with generation, adding
no wall-clock — one endpoint = ~12 h for the whole suite):

| Lane | median | mean | p90 | serial sum |
|---|---|---|---|---|
| V3, local vLLM (gen + judge) | 6.3 min | 9.6 min | 13.1 min | ~12.0 h |
| V2, hosted API, conc=40 (gen) | 7.1 min | 9.7 min | 22.3 min | ~15.3 h |

**The bottleneck is runaway reasoning**, not throughput: uncapped chains-of-thought stall
~6 min and return empty. Mitigation is baked in (`max_tokens=8192`, `REQUEST_TIMEOUT=150`,
retries; a trace with no final answer counts as empty and is retried). Residual empty rate
~1–3%/task.

**Endpoint requirements (per model):** 17,825 requests over ~12 h (~25/min avg), ~135 tok
in / up to 8,192 out each, ~40–100 concurrent, 16k context, no prefix caching needed;
mid-run outages recoverable via resume.

## Phase 2 plan: the 5-model batch

### Per model — endpoint in, scores out

| # | Step | Type | Time |
|---|---|---|---|
| 1 | **Intake & smoke test** — OpenAI-compatible? where does reasoning live (`reasoning_content` field → `--client local`; inline `</think>` → `--client k2think`)? probe rate limits *before* committing (skipping this cost 2 elapsed days on V2); 5-sample dry run read by eye | manual | 1–2 h |
| 2 | **Main run** — one tmux session; generation + interleaved judging | automated | ~12 h |
| 3 | **Run hygiene** — watch for empty-response streaks; quarantine corrupted tasks; swap judge key on credit cap | manual | ~1 h |
| 4 | **Sanity pass** — every task <0.8: read ~10 failing samples, model finding vs artifact | manual | 2–3 h |
| 5 | **Stage B + reports** — divergence judging over stored traces; add the model to `family_report/models.json` and rerun its two generators — the model's column/curves appear across all report tables and figures | automated | 2–4 h |

### Can we run all 5 in parallel? Yes — three caveats

1. **Per-model endpoint config:** ~10-line env-override patch (day-1 prep) so each tmux
   session points at its own endpoint; output dirs are per-model, results never collide.
2. **One shared judge key:** ≈74k judge calls (135k with Stage B). **Pre-load ~$400 (main
   scores) / ~$1,000 (full set)** — OpenRouter rate limits scale with balance, and both
   V3-era judging outages were mid-run credit caps. Judging is resumable if throttled.
3. **Only if endpoints don't share one GPU cluster** — 5 deployments on one cluster ⇒
   parallel ≈ serial. Question for the model team.

### Two-week schedule (one person)

| Days | Work |
|---|---|
| 1–2 | Prep (endpoint override, run scripts — report pipeline already built) + intake & smoke tests; launch all 5 runs |
| 2–3 | Runs finish (mostly overnight); hygiene; Stage B judging |
| 3–5 | Sanity passes + report review → **all scores final by end of week 1** |
| 6–10 | Family report prose (1–2 days; numbers/tables/charts auto-generate from `family_report/`) + buffer: staggered endpoint delivery, rate-limit storms, re-runs, key top-ups |

### Decisions needed before the batch starts

- [ ] **Endpoint shape** — OpenAI-compatible? Reasoning as field or inline tags? Rate limits? Shared cluster?
- [ ] **Score scope** — main scores only, or full set incl. thinking-divergence (+$100–130/model, no extra generation)?
- [ ] **Judge budget** — approve $400–1,000 on the OpenRouter key up front.
- [ ] **Keep n=200?** — required for apples-to-apples with V3/V2.

*(Decided: one family report covering all sizes — no per-model reports.)*

## How to reproduce — one command

The whole Phase-2 flow is automated by **`run_family.py`**: per model it smoke-tests the
endpoint, runs the full 95-task suite (generation + interleaved GPT-5.6-terra judging),
updates `family_report/models.json`, and regenerates the family report (charts + LaTeX).

```bash
# 1. describe the endpoints once (copy the template, fill in real URLs)
cp family_run.example.yaml family_run.yaml     # key, label, size_b, base_url, reasoning

# 2. run everything (add --parallel only if endpoints don't share GPUs)
.venv/bin/python run_family.py --spec family_run.yaml

#    handy variants:
#    --smoke-only     endpoint intake, stop before the full runs
#    --skip-smoke     endpoints already trusted
#    --report-only    rebuild manifest + report from finished runs (no eval)
```

Judge is set in `libra_eval/config/api_config.json` (`EVAL_MODEL=openai/gpt-5.6-terra`);
knobs `REQUEST_TIMEOUT=150`, `REQUEST_NUM_RETRIES=4` are already in place. Already-run models
(the V3 anchor, GPT-4o-mini) carry a `results_dir` in the spec and are reported without
re-running. Stage B (thinking divergence) stays a separate judge-only pass; point its
`thinking_csv` at the result in the spec to fold it into the report. Everything is resumable
— finished tasks are cached, so a re-invocation continues where it stopped.

*Measured baselines: K2-V3 (`outputs_full_200/`, Jun 2026), K2-V2 (`outputs_v2_200/`, Jul 2026).*
